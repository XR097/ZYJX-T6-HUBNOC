# HUB R-hub 易读版：四个计算核的部分和归约

## 先说结论

R-hub 是挂在 HUB 中心的一个小型归约单元。它只解决一种问题：当同一个矩阵乘的归约维 **K** 被切成四份，四个计算核各算出一份结果时，如何把四份部分和相加，再把结果送回指定的核。

它不是通用 NoC，也不是 L2 读改写引擎。R-hub 只接收四个核送来的 BF16 部分和，按固定顺序相加，按 32 个元素一组量化成 MXFP6，然后经 HUB-DN 的 VC2 返回归约属主核。

## 先解释几个词

- **K 切分**：矩阵乘 `Y = X × W` 中，沿输入/归约维 K 把计算拆给多个核。每个核只算完整结果的一部分，称为部分和。
- **部分和（psum1）**：K 维还没有全部合并的结果，R-hub 的输入格式是 BF16。
- **归约值（psum2）**：四路部分和合并完成后的结果，R-hub 输出为 MXFP6 g32。
- **BF16**：16 bit 浮点格式，R-hub 的中间加法格式。
- **MXFP6 g32**：每 32 个元素共用一个 E8M0 指数尺度、每个元素用 6 bit 表示的格式。一个输出组的载荷是 32×6 bit + 1 B 尺度，共 25 B；输入 SFD 格式码为 8，输出 SFD 格式码为 12。
- **pid**：一个位点内输出组的顺序编号。R-hub 不给每条部分和携带地址，因此四个核必须按同样的 pid 顺序发送。
- **归约属主核**：一组归约结果最终要回到的计算核。属主核编号放在上行 VC2 的 14 bit 侧带头中，由 CCU_CTL 提供；R-hub 不在条目中携带 pid/token 标签。

## 数据怎么流

```text
CC0 F1b/E6 出口队列 ─┐
CC1 F1b/E6 出口队列 ─┼─ 上行 VC2 ─> R-hub 入口 FIFO
CC2 F1b/E6 出口队列 ─┤
CC3 F1b/E6 出口队列 ─┘

四路 FIFO 头部对齐
        ↓
固定顺序 BF16 加法树
        ↓
连续两条 16 元素结果拼成 32 元素组
        ↓
amax / E8M0 / MXFP6 g32 量化
        ↓
D-40 VC2 返回归约属主核
        ↓
核内 L1 AB 停放区 → NLU/后续向量处理
```

每个输入条目含 16 个 BF16，即 256 bit，正好对应一个 32 B flit。四个核各有一个入口 FIFO，深度以参数实现（16 条为参考默认值，待冻结）。四路 FIFO 的头部都有效时，R-hub 才处理一条条目；因此输入 FIFO 与 HUB-UP 的 L2 写口路径完全分开。FIFO 信用返还由 HUB-UP 产生，R-hub 只提供 pop 事件。

## 加法顺序必须固定

每个 lane 做两级加法：

```text
s01 = RNE_BF16(c0 + c1)
s23 = RNE_BF16(c2 + c3)
y   = RNE_BF16(s01 + s23)
```

`RNE` 是 round-to-nearest-even，即“就近舍入，正好在中点时取偶数”。固定顺序的目的是让结果只由输入值决定，而不受四个核的到达顺序、回压或网络拥塞影响。

参与核少于四个时，缺少的输入按 **+0** 处理，但加法树结构和顺序不变。R-hub 不做跨拍累加；每条对齐后的输入独立通过流水线。

## 量化与回送

同一流中相邻两条 16 元素结果组成一个 32 元素组。第一条结果需要暂存 32 B，第二条到齐后才进行量化：

1. 计算 32 个 BF16 元素的绝对值最大值 `amax`。
2. 根据 `amax` 生成共享 E8M0 尺度。
3. 将 32 个元素量化成 MXFP6 E2M3 g32。
4. 形成 25 B 数据，并在 32 B flit 剩余 7 B 中携带按归约属主核计数的 16 bit 组序号；计数器清零时机仍待审查。
5. 根据归约属主核，把结果交给 HUB-DN 的 VC2；量化参考模型必须与后处理单元的量化点逐位一致。

R-hub 本身不选择 D-40 的具体道，由 HUB NoC 选择最空道。归约属主核的落地口根据 VC2 类别字段把结果写到 AB 停放区，LAND 用组序号将它与 token/列块对应起来。

下行回送使用 VC2 类别 0；落地 FIFO 的初始信用、VC2 与数据 VC 共用的 `wD` 保底槽，以及 R-hub 与 HUB-SYNC 共用 VC2 时的仲裁均由 HUB-DN/HUB-UP 合同确定。

## RTL 可以怎样拆

下面是用于 RTL/验证评审的派生实现分解，不是 PDF 新增的架构子单元。建议先拆成以下几个单元：

1. `rhub_ingress_fifo`：四路 VC2 接收 FIFO，产生满/空和 pop 事件；信用返还由 HUB-UP 统一发出。
2. `rhub_head_align`：检查四路头部是否都有效；维护参与核掩码和 pid 顺序假设。
3. `rhub_bf16_tree`：16 lane、两级固定顺序 BF16 RNE 加法。
4. `rhub_group_buffer`：缓存同一组的第一条 16 元素结果。
5. `rhub_mxfp6_quant`：32 元素 amax、E8M0 生成、E2M3 编码、RNE 和限幅。
6. `rhub_egress`：拼接组序号和侧带字段，向 HUB-DN VC2 发出。

参考设计是 16 lane，每拍处理一条 16 元素条目，即每两拍完成一个 32 元素组。入口对齐 1 拍、两级加法各 2 拍、量化 2～3 拍、到齐至回送不超过 10 拍均为【待标定】参数；PDF 图注另写“32 lane”，该冲突列入未决项。

一致性目标为与 FP32 精确和再量化结果至少 99.9% 一致，不一致处最多差 1 个码【待标定】。面积参考约 0.084 mm²、48 个 BF16 加法器和 2,080 B RF【一阶推导】；这些数字随 lane 数、FIFO 深度和工艺映射冻结。

## 必须验证的行为

- 四个核按相同 pid 顺序发送时，输出与参考模型逐位一致。
- 输入到达顺序不同、任意一路被回压时，最终结果仍逐位一致。
- 任一路入口 FIFO 满时，只反压对应核，不错误阻塞其他核的输入。
- 第一条 16 元素结果会被正确保留，第二条到齐后才量化。
- BF16 两级 RNE 顺序固定，不能被综合优化成不同的加法树。
- MXFP6 的 E8M0、6 bit 编码、RNE、限幅和按 owner 计数的组序号正确。
- 属主核字段能正确决定 D-40 回送目的地。
- VC2 信用和入口 FIFO 深度不会溢出。

## 当前明确和未明确的内容

已经明确：R-hub 只服务 Qwen Prefill 的 gate/up K 切分；不写 L2；不做 key 匹配；不做残差加；不做 gate/F/C/Z 判决；不服务 MiniCPM 当前的 N 切分。

仍待确认：MiniCPM 旧版本 VC2 带宽口径、精度验收线、流水级数、down/o K 切分是否启用、16 lane 与 FIFO 深度是否最终固定，以及面积/门数估算。详见原需求文档末尾未定项。
