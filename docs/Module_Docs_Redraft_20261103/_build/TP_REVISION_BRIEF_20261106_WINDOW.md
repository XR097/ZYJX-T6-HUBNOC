# 压紧激活按位点窗口静态分配（V18-TP-40、V18-SEL-13）——改稿任务书

> Owner: WangYizhao｜2026-11-06｜用户原话："我认为 Activation 数据虽然要被压缩，但是可以在算法侧预先给出一个典型窗口，去保证每个数据都能被存储到该窗口，这样还可以极大程度简化调度逻辑。并且这个窗口需要以每个计算为单位去调整"；"我认可这里的设计"。取代 V18-TP-19 的 bump 分配；关闭 V1.8 §4 的 U-TP-4。Agent 只改本任务书点名的正式稿与脚本，不改 `Claude_Design_Spec/`、目录稿、ISA。

## 1 新规则

### TP-40 压紧激活对象按位点窗口静态分配，撤 bump 分配

- **每个位点的压紧激活对象**（协议篇 §9.2 第 ③ 档：前向紧凑激活记录、反传流动梯度 dX / dY / dH / dP / dS / dz、Q 粗算记录、$P'$ 记录、位图、列表、TOPK 项、参与词号列表）**有一个由算法侧给出的窗口（上限长度），编译链按窗口静态分配源空间与目的空间（L1 与 L2），所有基址写在位点指令与发送指令里；CCU 不再做 bump 分配，也不再有"下一个对象从上一个结束处开始"的运行期依赖。** 窗口按位点配置，随模型表进调用（CCU 指令里的"对象上限 / token 槽长"字段由"只给并发增长的槽"改为每个位点必填，ISA 侧登记）。
- **窗口的算法**：窗口 = 封顶后的记录长度上限 × token 数（记录长度上限 = $k$ + 本域强制入选数对应的元素数 × 元素位宽 + 段头，按记录补到 32 B 整数倍；参与词号列表 = 两组流式 TOPK 的 $k$ 之和）。**不再有"不封顶位点取全保留长度"一说**——见 SEL-13。token 驻留与权重驻留两种拼接顺序都在同一窗口内（§9.7 的 token 槽就是窗口按 token 切成的槽）。
- **超出窗口 = 致命错误**（§10 原"token 槽超上限"扩展为"任何压紧激活对象超窗口"），由 SEL / QNT 按封顶模式保证不发生。
- **发出报告与长度转发仍带实际长度**（单位数、总存储字数、记录数、尾字字节）；读方按实际长度读，不读整个窗口；写计数的应写量按实际写入项数比对（§2.6 不变）。
- L2 目的端：编译链按窗口预留，目的基址在 CCU 的发送指令里（关闭 U-TP-4）。
- 代价写进"为什么"：窗口留在上限时的空间空着，窗口大小直接决定一核能驻留多少 token，所以封顶值是算法侧按精度与容量一起定、按位点调的旋钮。

### SEL-13 存储或传输的压紧激活一律用有封顶的选择模式

- 凡产出要存进 L1 / L2 或经链路传输的压紧激活的位点，SEL 的选择模式必须有封顶：流式 TOPK，或"阈值后封顶"（阈值 + 最多 $k$ 个）；纯阈值（不封顶）模式只允许用于不落盘、不传输的判决。封顶值 $k$ 由算法侧按精度与容量定、按位点配置，算法评测按封顶后的结果测精度。SEL 保证选出个数 ≤ 封顶，QNT 保证写出记录 ≤ 记录长度上限。
