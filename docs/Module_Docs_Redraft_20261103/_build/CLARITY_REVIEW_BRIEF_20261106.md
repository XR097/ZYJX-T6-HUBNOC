# 正式稿清晰度遍历任务书（11-06）

> Owner: WangYizhao｜2026-11-06｜用户原话："你现在又出现描述不清晰的情况了……你只进行这么简短的描述，设计者没办法知道要做什么，我建议你对正式稿都进行一次遍历，确认是否有这样不清楚的描述内容"。被点名的样本是 `MAE_NI_INT.md` §5.6（原两句"速率背景"）与 §5.7（原一句"通用链路块"），已改写成表格 + 逐条要求，**先读改后的这两节，照这个标准改**。

## 1 什么算"不清楚"

读者是要把这篇做成 RTL 的设计者。一段文字如果他读完答不出下面任一问题，就是不清楚：

1. **做什么**：这个部件 / 这条规则要我实现的动作是什么（输入什么、做什么、输出什么、什么时候生效 / 切换）。
2. **量纲**：数据是什么张量 / 记录 / 消息，沿哪一维，每次几个元素，每个元素几位；速率是每拍多少、按哪个时钟。
3. **为什么是这个数**：给了数字的，要说明是要求值、参考值还是推导值，适用什么工况；给了【设计者定】的，要说明他要定的是什么、受什么约束。
4. **边界**：超额、冲突、空、满、乱序时怎么办——是错误、还是降速、还是由谁保证不发生。
5. **接口**：对端是谁、几条、每条的信号与位宽；引用别篇时，本篇至少要写清"本篇的这一侧"要做什么，不能只写"见 X 篇"。

典型的不清楚写法（都要改）：
- "只作背景：……"后面只有一个公式；
- "都是通用链路块的实例"而不列出哪些实例、各自的位宽与旁带；
- "按协议篇 §x"而本篇不说本侧要做的事；
- "匹配上下游""视情况""【设计者定】"而不说要定什么、约束是什么；
- 用"宽数据 / 窄激活 / 快边 / 慢边"这类相对称呼代替对象与量纲（AGENTS.md 写作规范第一条）；
- 一句话带过一个会占几百行 RTL 的部件（仲裁器、缓冲、计数器、FIFO）而不给输入 / 输出 / 规则。

## 2 怎样改

- **只把已经定下的内容写清楚**：依据是协议篇、V1.8（`Claude_Design_Spec/V1.8_DESIGN_REVISIONS.md`）、各篇自己的其他节、V1.7_3 冻结基线中未被 V1.8 取代的条款。**不得新发明设计、不得新给数字**；现有数字要标明是要求值 / 参考值 / 推导值与工况。
- 真的没定过的，写成"【设计者定】：要定的是 X，约束是 Y"；若连约束都没定过，不要编，列进报告的"未覆盖项"交用户。
- 改法优先用表（接口表、实例表、来源表、要求表）和编号的要求条目；决定行为的一句加粗。
- 不改章节结构、不改设计、不改图、不动其他目录的文件、不改 `Claude_Design_Spec/`。
- 每篇改完在文件头修订记录加一行"11-06 清晰度遍历：改写了 §…"。
