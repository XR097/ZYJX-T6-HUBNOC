# HUB NoC / R-hub 架构与 spec 阶段待定事项

日期：2026-10-28
依据：HUB_NOC、HUB_RHUB、SPEC_TRANSFER_PROTOCOL_V1.5（下称"协议篇"）、DATA_LAYOUT_V1.5 四份 PDF，页码取 PDF 页脚。

## 0. 这份清单收什么

只收当前阶段（架构设计、模块 spec 撰写）必须定下来的事：接口字段与编码、模块之间的分工边界、架构取舍，以及措辞需要确认的地方。这些事不定，模块 spec 的接口章节写不完，或者两个模块的 spec 会对不上。

不收的有三类：需要周期级仿真才能回答的（时延实测、深度回填等），机制已定只差数值标定的（精度、面积、时延目标），以及不属于 hub 的。这些项的说明见 `open_issues_ledger_v2.md`，本文附录列出了去向。

编号沿用 `open_issues_ledger_v2.md`，便于对照。OI-22 至 OI-25 是这次新增的，都是撰写 spec 时才暴露出来的缺口。标"推导"的项，PDF 没有直接写，是从原文前后对照得出的。

一条总原则（AGENTS.md）：协议篇是协议权威，HUB PDF 是模块合同。带宽、VC 语义、侧带位宽和归属边界不能在 spec 里悄悄改。下面所有"建议答案"都只在这些已定框架之内补空白，不动框架本身。

## 2. A 类：确认措辞即可关闭

这三项旧台账登记为"冲突"，复核后不是冲突，只是个别句子写得不完整。之所以放在 spec 阶段，是因为 Codex 已经按"冲突"在 spec 里留了开关或限制（如 `SHARED_POOL_RATE_MODE`），措辞不确认，这些临时设计就删不掉。

**OI-12 VC2/VC3 每拍限速。** VC2、VC3 的信用按（核, VC）共享池计。为了让核侧每个 VC 只需一个单写入落地 FIFO，hub 对同一核每拍限发。问题是"VC2、VC3 各 1 flit"还是"两者合计 1 flit"。HUB_NOC p8 §4.1.5 原文是"每拍各至多发 1 flit"，协议篇 p19 §4.4.4 的理由（各一个单写入 FIFO）也只要求各自限速，两篇的协议断言（协议篇 p22 §4.4.13、HUB_NOC p9 §4.1.7）检查的也是单个 VC。只有协议篇 p25 §5.3 和 §6 的汇总句漏了"各"字。请协议篇作者确认"各 1"并补字；确认后 spec 删除 `SHARED_POOL_RATE_MODE`（00、01、02 文档中有引用）。

**OI-13 D-40 的"4 道"。** 发送侧：hub 中心有 4 个道发端，每个对应一个 L2 象限，各 32 B/拍，合计 128 B/拍（HUB_NOC p1 §1.1；DATA_LAYOUT p2）。接收侧：每个核都接了这 4 道，所以协议篇写"每核 4 道、每核 128 B/拍"（p1 §1.1、p8 §3.1）。多播时四核同拍收到同一份数据，四核合计不会到 512 B/拍。请协议篇作者确认，并把措辞改为"每核最多接收 4 道 = 128 B/拍，四核共享中心 4 个道发端"。确认后 spec 按 4 个道发端写，删掉"RTL 前禁止据此定复制数量"的限制。

**OI-18 R-hub lane 数图注。** HUB_RHUB p3 图注写 32 lane，正文 §4.1.1、§5.3、§7 已按 54 号 C54-13 改为 16 lane 参考设计，§5.2 也说明 0.084 mm² 是 32 lane 的上界。只是图注没跟着改。请 HUB_RHUB 作者改图注；R-hub spec 按 16 lane 默认、参数化书写。

## 3. B 类：接口字段与编码

这一组决定模块 spec 的"接口"章节能不能写完。PDF 普遍的写法是"字段次序与编码为建议值，实名与位宽交 ISA 与设计者"（协议篇 p18）。如果一直等 ISA，spec 就只能写"见 ISA"。建议的做法是：先把 PDF 建议值作为 spec 的冻结基线，并在 spec 中注明"ISA 有异议时按变更流程改"，这样各模块 spec 至少彼此一致。

### OI-01 子字节位序、SFD 编码、侧带头编码

**背景。** 激活和权重大量使用 2、4、6 bit 元素，一个字节里装好几个码。打包端和解包端位序不一致，数据就会整体错位，而且仿真里很难一眼看出来。SFD（载荷格式描述）是每条流的"说明书"，告诉格式感知端点（HUB-DN 段片切分、HUB-ATT、R-hub、核侧落地口）怎样定位每个元素。

**PDF 已给的建议值。**

- 位序：低位在前，码 i 占值区第 [w·i, w·i+w) 位，字节 b 存第 [8b, 8b+8) 位，并给了一个可核对的例子（5 个 E2M3 码 → 0x1C 0x4B 0x21 0x38）（协议篇 p12 §4.1.3）。
- SFD：类别 4 bit、位宽 3、组大小 2、尺度放置 2、平面数 2、长度来源 2、计数 ≤ 24，合计约 39 bit 一条流；类别码 0–13 已逐一列出（协议篇 p11 §4.1.2）。
- 侧带头：下行 12 bit（掩码 4、VC 2、类别 3、末拍 1、nw8 2），上行 14 bit（再加属主号 2、区域号 4），类别取值按 VC 列出（协议篇 p17–19 §4.4.1–4.4.2）。

**未定的是什么。** 三者都标"建议值，随 ISA 确认"（协议篇 p11、p12、p18、p26 §7）。字段内容和位宽总数是协议权威给定的，不能改；未定的只是字段次序、实码和位序。

**为什么现在要定。** hub spec 的接口章节、HUB-DN 段片切分和 R-hub 入口解析都要写到位级。等 ISA 定案再写，spec 就一直缺接口定义。

**建议。** spec 直接采用协议篇建议值作为冻结基线，注明来源与"ISA 有异议按变更流程改"。需要 ISA 负责人确认一次：是否接受这个做法，或给出 ISA 冻结时间。

### OI-23 VC3 消息类型码与字段（新增）

**背景。** 位点完成、WB 槽释放、份释放、属主核完成、系数就绪、gather 计数、GO 七种事件都走 VC3，不拉专线。每条是单 flit（属主核完成至多 3 flit），"首字节为消息类型、其余为字段"（协议篇 p22 §4.4.12；HUB_NOC p15 §4.5.8）。除这七种外，VC3 还承载核描述符转发、判决广播、区块并集广播、档表同步，以及随机数、父槽表、TAG 表、祖先掩码块、节点档表、Batch 行表等表装载（HUB_NOC p6 §3.2、p10–11 §4.2.8–4.2.9、p13 §4.4.5、p14 §4.4.10）。

**hub 为什么必须知道类型码。** 上行 VC3 进 hub 后，HUB-UP 要按类型分流到不同去处：份释放直达 NI 的 SDN（协议篇 p8；HUB_NOC p15 §4.5.7），WB 槽释放直达 MAE（HUB_NOC p6），档表同步要转成 D-40 VC3 多播，位点完成交 HUB-SYNC 计 barrier。也就是说，hub 的 VC3 分流表就是按首字节查表。四份 PDF 里都没有这张类型码表，也没有各消息的字段布局（位点完成要带位点号和 nflit，HUB_NOC p14 §4.5.4）。

**为什么现在要定。** 不定，HUB-UP 分流逻辑、HUB-SYNC 的 barrier 输入接口、hub 到 SDN 和 MAE 的事件接口都写不了；CCU_CTL、MAE_NI_INT 两侧的 spec 也会各编一套。

**建议。** 由协议篇（或 CCU_CTL 篇）补一张"VC3 消息类型表"：类型码、发送方、接收方、字段与位宽、flit 数。hub spec 引用这张表，分流规则按"类型码 → 目的"写成表格。

### OI-22 列表环数量与环号分配（新增）

**背景。** 列表环是 L2 固定区里的环形缓冲，各核产生的列表（录取并集、键号列表等）由 HUB-ATT 写入，MAE 按列表读。上行 VC1 的类别 1（环写）用 4 bit 区域号表示环号，HUB-ATT 按环号维护写指针和满标志（HUB_NOC p12 §4.3.5）。

**不一致之处（推导）。**

- HUB_NOC 写的是 9 个：录取并集、lo 读集、TOPK 列补算、接受路径、键号、重算、掩码镜像、区块列表、S 列表，并注明"与 L2 SRAM 篇 §4.3.1 一致"（p2 §1.4、p4 图、p16 §5.2）。
- 协议篇写的是"环写时为环号，8 个环在内"（p19 §4.4.2，p18 图中同样写"8 个环"）。

看起来是协议篇在 V1.5 加入 S 列表环（57 号 B-26）后没有同步更新。4 bit 区域号能编 16 个，9 个也放得下，所以侧带位宽不受影响。

**还有一个缺口。** HUB_NOC p12 §4.3.5 列出的 LM Head 属主核环写对象里，还有"属主核结果区"和"片上建树的树记录组"。它们不在 9 个环之列，同一节后文又说"类别 0（区域写）的结果区与其他区域由 HUB-UP 按（核, 区域）游标生成地址"。HUB_NOC p6 也把结果记录、树记录组列在"类别 1 环写"下。结果记录究竟走环写（HUB-ATT）还是区域写（HUB-UP），两处说法不一。

**为什么现在要定。** HUB-ATT 的环表大小、HUB-UP 对 VC1 的分流规则（类别 1 → HUB-ATT，类别 0 → 游标表）都依赖这一点。环号表不定，核侧发环写时用什么号也没法写进各核 spec。

**建议。** 以 HUB_NOC 的 9 个为准，请协议篇作者把"8 个环"改为"9 个环"。由 HUB_NOC 和 L2_SRAM 作者补一张环号表（环号 0–8 分别对应哪个环）。结果区和树记录组请作者明确：要么编环号走 HUB-ATT，要么写明走类别 0 区域写。

### OI-24 hub 位点描述符的字段级格式（新增）

**背景。** hub 位点描述符由 LIC 按（阶段, 层, 位点）下发，随 GO 生效（HUB_NOC p6 §3.2）。PDF 列出了它的内容：目的掩码与 D-40 发送表、部分和读回表、wD（4 bit）、R-hub 归约配置（使能、参与核、属主映射）、位图 OR 与列表环配置（参与核掩码、kv 头 → 核映射、OR 粒度、Batch 段号）、判决广播映射、barrier 模式、HUB-UP 各（核, 区域）的游标基址/长度/回绕，以及本位点各条下行流的 SFD。

**未定的是什么。** 只给了"按含义"的内容清单，没有字段位宽、排布、条目数上限，也没有说 LIC 控制口怎样装载（一次整块写入还是逐字段写、是否有双缓冲）。已知的尺寸线索只有：SFD 每条约 39 bit、一个位点 3 到 6 条流（协议篇 p24），以及 HUB-UP 每核约 16 个 21 bit 游标（协议篇 p19 §4.4.3）。

**为什么现在要定。** 这是 hub 对 LIC 唯一的配置接口。hub_control 的寄存器定义、各子单元从描述符取哪些字段、LIC spec 的输出格式，都等这张表。Codex spec 目前用 `DESC_ENCODING` 参数留空（01 文档 §5）。

**建议。** 由 HUB_NOC 作者（或 LIC 作者）补一张描述符字段表：字段名、位宽、条目数上限、由哪个子单元使用。"GO 后统一生效"已定，装载方式（是否双缓冲）请一并写明。

### OI-03 上行位图怎样标明归属；区块 OR 粒度编码

**背景。** HUB-ATT 收三类上行 VC0 位图：录取位图（按（层, kv 头, 64-key tile）合并）、区块位图（按（层, kv 头, 查询波次）合并）、lo 读集位图（按（位点, 列块）合并）（HUB_NOC p3、p12–14 §4.4.1–4.4.10）。合并缓冲按（在飞 tile 数 × kv 头数）定容，每项 64 bit 位图加参与核到齐位（p13 §4.4.6）。区块大小按位点可配，64·2^eblk key，eblk = 0…3，记录最长 512 bit（p14 §4.4.10）。

**未定的是什么。** HUB_NOC §7 登记的是"区块位图的记录格式与 OR 粒度编码"（p18）。往下看，缺口其实更大一点：上行位图本身怎样告诉 HUB-ATT 它属于哪个 kv 头、哪个 tile 或波次，PDF 没写。是带标签（在载荷里放一个短头），还是像 R-hub 那样不带标签、按各核发送次序对齐，也没写。上行侧带头里只有类别（区分录取 / 区块 / lo 读集），没有 tile 号或 kv 头号。Batch 一条又要求"每条记录带段号"（p14 §4.4.11），说明至少 Batch 下位图是带头的。写进 L2 的列表环记录有统一的 8 B 头（模板号 4、序号 16、格式位 1、计数 16）（DATA_LAYOUT p20），但那是 HUB-ATT 的输出格式，不是上行输入格式。

**为什么现在要定。** 这决定 HUB-ATT 合并缓冲怎样寻址、怎样判断到齐，是 HUB-ATT spec 的核心。

**建议。** 三类位图共用一个上行位图头，放在载荷里（不改 14 bit 侧带），至少含 kv 头号、tile 或波次序号、段号；OR 粒度不另编码，直接用描述符里的 eblk。由 ATT 作者和协议篇作者确认。

### OI-05 S 列表环记录格式与长度

**背景。** 训练 LOSS 归并时，链首训练核把 dH 支撑集 S 列表经上行写进 S 列表环，MAE_ENG 按列表 gather（HUB_NOC p12 §4.3.5，57 号 B-26）。

**对 hub 的影响。** hub 只维护环号、写指针和满标志，记录内容透明搬运。只要 S 列表沿用列表环通用的 8 B 头（模板号、序号、格式位、计数），HUB-ATT 就不需要专门逻辑。

**建议。** hub spec 按"通用列表环、记录格式透明"写，不等这一项。记录格式和环长由 MAE 与训练链首核的数据合同确定；若 S 列表不用通用 8 B 头，请作者提前告知。

### OI-06 Batch 合并键

**背景。** Batch 下每行能看到的 KV 分两段：共享前缀段和本行私有段。前缀段的 tile 对全部行、全部参与核取并集，读一次多播给各行；私有段只合并持有该行的核的位图，不同行同一 tile 号的私有 tile 不合并。所以 HUB-ATT 的合并键要加段号，期望到齐数"按该段的参与核掩码派生"（HUB_NOC p14 §4.4.11）。

**未定的是什么。** 段号位宽，以及私有段的参与核掩码从哪里来（HUB_NOC p18 §7）。线索：Batch 行表每行 16 B，含私有段基址与长度，32 行 512 B（DATA_LAYOUT p21）。

**为什么现在要定。** 合并键宽度决定合并缓冲的 CAM/索引宽度；掩码来源决定 HUB-ATT 要不要自己保存行 → 核映射。

**建议。** 段号位宽按最大批行数定。若以行表容量 32 行为上限，私有段需 5 bit，加上前缀段的编码共 6 bit。私有段掩码由 hub 位点描述符直接给（"行 → 参与核掩码"表），HUB-ATT 不自行推导。请 ATT、CCU_CTL 与数据流作者确认最大行数和掩码来源。

### OI-04 chunk 池偏移索引对齐

**背景。** 上行 flit 不带地址。HUB-UP 按描述符给的（核, 区域）基址、长度、回绕生成写游标，同一区域写序等于到达序（协议篇 p19 §4.4.3）。chunk 池里的 token 记录是变长的（稀疏激活紧凑记录，DATA_LAYOUT p11），读端要能按 token 找到记录，需要偏移索引。偏移索引怎样对齐"按 L2_SRAM 篇的区域规则"【待审查】。

**为什么现在要定。** 这决定 HUB-UP 游标是否需要按 token 对齐跳格、是否要额外写一张偏移表，属于 HUB-UP spec 的游标条款。

**建议。** 请 L2_SRAM 作者给出 chunk 池区域规则（token 记录按多少字节对齐、偏移表由谁写）。hub spec 的游标条款在此之前写"按区域规则对齐"并引用 L2_SRAM 对应条款。

### OI-19 R-hub 回送目的的属主号来源

**背景。** R-hub 把四个核的部分和相加后，结果要回送给这一组的归约属主核。属主按 token 交错指定（HUB_RHUB p2 §1.4）。PDF 里属主信息有两个来源：

- 上行 VC2 侧带头带 2 bit 归约属主号，由 CCU_CTL 给出（HUB_RHUB p3 §3.1、p6 §6；协议篇 p19 §4.4.2"属主核号 2 bit（VC2 用）"）。
- hub 位点描述符给出"是否启用归约、参与核集合与属主映射"（HUB_RHUB p3 §3.1）。

PDF 没说以哪个为准；若取 flit 头，也没说取参与核中哪一路。

**为什么现在要定。** 这是 R-hub 回送目的选择的唯一输入，不定 R-hub spec 无法写出口逻辑。

**建议。** 以上行 flit 头的属主号为准，取固定的一路（如参与核中编号最小的核）。理由是协议篇专门为 VC2 设了这 2 bit，而属主按 token 交错，逐 token 的信息天然在 flit 上。描述符的"属主映射"只用于验证比对。四路属主号不一致只可能是各核放行次序错位，HUB_RHUB p5 §4.2.1 已规定"R-hub 不检测序错位，序一致由核侧保证并在验证中覆盖"，所以不一致的检查放进验证断言，RTL 不新增错误路径。请 HUB_RHUB 与 CCU_CTL 作者确认。

### OI-25 "hub 配置口"所指不明（新增）

**背景。** 阈值套"经 VC3 或 hub 配置口"装进各核 SEL 阈值表（HUB_NOC p5 §3.1、p10 §4.2.8）。但 hub 的端口清单里只有"LIC 控制口"（p5），没有单独的"配置口"。

**为什么现在要定。** hub spec 要列出完整端口清单。若"hub 配置口"是另一个物理口，就要定义它；若就是 LIC 控制口，阈值套又是要装进各核的，最终还得经 D-40 VC3 下发，两种说法其实是同一条路。

**建议。** 请 HUB_NOC 作者写明"hub 配置口"即 LIC 控制口，或删去这几个字，只保留 VC3。

## 4. C 类：架构决定

### OI-10a 调用内改写档表同步的时延预算

**背景。** Verify 时旁路判别器可以在一次调用中途改写节点档表（0/1/2 三档，决定各节点走多重的计算）。LM Head 属主核改完本核档表后，如果 attention 也按档分级，新档表要经上行 VC3 进 hub，再由 D-40 VC3 按参与核掩码多播给 attention 帮手核，在下一个位点边界与属主核同时生效；同步完成计数到齐前，该位点不放行（HUB_NOC p11 §4.2.9）。

**未定的是什么。** 机制已定，但没有规定这次同步最多允许多少拍（HUB_NOC p18 §7【待审查】）。同步慢了，下一位点就要等，Verify 每轮都会被拉长。

**为什么属于本阶段。** 这不是测出来的数，而是一条架构预算：它决定 hub 是否要给档表同步专门的优先级，或者只靠控制 VC 严格优先就够。控制单程 p99 ≤ 12 拍、barrier 约 46 拍已有预算（HUB_NOC p7 §4.1.2、p17 §5.4），可以作为参照。

**建议。** 架构与算法侧给一个拍数上限，写进 HUB_NOC §5.4 的时延目标；hub 侧只做"超预算计数"，不加专用通路。若控制 VC 现有预算（上行 + 下行各 ≤ 12 拍）能满足，直接写明即可。

### OI-20 down / o 的 K 切分

**背景。** K 切分是把一个输出的归约维分给多个核，各核算部分和，由 R-hub 相加。现行只有 Qwen Prefill 的 gate/up 用 K 切分。down 与 o 的 K 切分是预留扩展，默认不启用，"启用时沿用本篇的固定次序与出口量化，不改结构"（HUB_RHUB p5 §4.3.4）。启用条件与启用后的容量标为【待审查】（p7 §7）。旧台账 05 未登记。

**为什么属于本阶段。** 这决定 R-hub spec 的定容口径：如果本期就要支持 down / o，入口 FIFO 和吞吐要按更大的负载核算；如果不支持，R-hub spec 只需写一个位点使能。

**建议。** 本期不启用，R-hub spec 按 gate/up 负载定容，只保留位点使能位。是否启用、启用后容量由数据流篇在下一版给出。请负责人确认"本期不启用"。
